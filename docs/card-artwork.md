# Saved static card artwork (opt-in)

Each owned catalog deck can have independent named static-artwork sets, such as Claude and GPT, over the same cards. Stable deck resource ID, pack ID and card slug select a slot. Omitting the pack ID preserves the original `saved-artwork` set. DeckManifest remains semantic content; artwork returns a separate, portable VisualPackManifest. Replacing artwork never rewrites card meanings, authored source, or executable programs.

## Website and MCP

- Signed in: open a deck, choose **Artwork**, create or select a visual set, then select a card and PNG/JPEG/WebP file and save. The card browser and reading view share the per-deck selected set. The website accepts at most 3,000,000 input bytes and 16 million pixels. Raster artwork appears in the card browser/detail; other cards keep their existing semantic fallback.
- MCP: `create_visual_pack({deckId,packId,label,description?,expectedDeckRevision})` creates a named set without changing existing images. IDs use lowercase words separated by hyphens/dots/underscores, up to 80 characters; labels are up to 80 characters, descriptions up to 500. `saved-artwork` is reserved. There are at most 32 named sets per deck. Repeating identical creation metadata is idempotent; conflicting metadata returns a conflict.
- `get_card_artwork` accepts optional `packId`; set `includeImage:false` for compact metadata, current deck revision and prior artwork ID. `set_card_artwork` takes exactly one native `file` (up to 5,000,000 bytes) or canonical `base64` (up to 1,000,000 decoded bytes), plus `mediaType`, stable deck ID, card slug, optional pack ID, expected deck revision and prior artwork ID (null for the first image **in this set**). A conflict requires refreshing and an intentional retry, never silently overwriting a newer upload.
- `list_visual_packs` includes named saved sets, including empty sets and completion counts. The legacy default set is listed when it has front artwork, a cover, or a stored back. `get_card_art` and `render_reading` honor an explicit `packId` strictly: missing artwork never borrows an image from another set. A partially illustrated spread reports missing art rather than fabricating a completed deck. In the website, missing artwork shows the semantic card face.
- Native file input uses the host's `openai/fileParams` contract and a restricted ChatGPT file-delivery downloader. Owner/set/revision checks run before downloading; URL origin, public DNS, redirect refusal, byte and time limits, raster validation and re-encoding remain enforced. Arbitrary URLs and local filesystem paths are not accepted. Actual generated-file availability still depends on the client; a displayed image is not proof that the host can transfer it. Inline base64 or downloading and uploading through the signed-in website remain fallbacks.
- The 5,000,000-byte allowance applies only to the server's outbound native artwork fetch and trusted normalization path. The MCP request carries a small file descriptor, not those image bytes. Website/raw artwork remains limited to 3,000,000 bytes, inline artwork to 1,000,000 decoded bytes, manifest files to 2,000,000 bytes and the default MCP request body to 4,000,000 bytes. Native fetch still has a 15-second deadline; normalized output and all raster/security limits below are unchanged.
- SVG rasterization and animated/p5 program execution are **not implemented**. Existing portable program declarations/source remain untouched. Static fallbacks can be uploaded separately. Nothing in this feature runs user-authored code or fetches arbitrary user-supplied URLs.

## Website covers and stored card backs

Each visual set optionally owns one `cover` and one `cardBack`. They are image bindings on `VisualPackManifest`, outside the semantic deck manifest and outside `cards`. A cover/back-only visual pack is valid. The two assets are never synthetic card slugs and never increase `cardCount` or front `complete`: 78 card fronts still means 78/78, whether either extra image exists or not. `hasCover` and `hasCardBack` report the separate slot coverage.

- The website Artwork editor accepts cover and back uploads for the selected set. Covers appear in My Decks, Community and the deck landing page. Missing covers keep the existing glyph; another set's artwork is never substituted. When several populated sets exist, the website uses the user's selected set or asks for a choice.
- Card backs are stored and previewable in the editor only. This change does not enable face-down cards, flipping, reveal interactions, or a reading-renderer overhaul. An absent back remains absent.
- Use a back matching the card-front proportions; 180-degree rotational symmetry is recommended when reversals should not be revealed by the back. Covers may use a different composition. Upload normalization and website previews preserve aspect ratio without cropping. There is no image generation or automatic artwork derivation in this feature.
- MCP: `get_visual_pack_asset({deckId,packId?,slot:"cover"|"cardBack",includeImage?})` retrieves the exact slot, with the same metadata-only option as card artwork. `set_visual_pack_asset` takes those slot identifiers, the same `mediaType` and exactly-one `file`/`base64` inputs, `expectedDeckRevision`, and `expectedArtworkId` (null for an empty slot). Missing slots return not found; inspect `list_visual_packs` flags and the current deck revision before first upload. Omitted `packId` consistently means `saved-artwork` on these low-level asset tools.
- HTTP: `GET /api/decks/:id/artwork/assets/:slot?packId=...` returns metadata; append `/image` before the query and supply `version` for bytes. `PUT /api/me/decks/:id/artwork/assets/:slot?packId=...` uses the existing `x-arcana-deck-revision` and `x-arcana-artwork-version` headers. Selected-set catalog responses add nullable `cover` and `cardBack` metadata. Older responses lacking these fields remain valid to the browser client.

Cover/back uploads share the existing owner/visibility, OAuth, native-file allowlist, byte/pixel limits, normalization, quota and decode-concurrency controls. Attachment compares the exact `(deck_id, pack_id, slot)` under the same owning-deck lock; replacement cleans up only that slot's old object. Private reads verify bytes and recheck current visibility after storage retrieval. Fronts, covers and backs remain independent across sets.

## Security and lifecycle

Uploads require the current owner and deck read+write scopes. Metadata/image reads follow the deck's current private/unlisted/public permissions. Private object keys, credentials, provider URLs and owner IDs are never returned. Reencoding strips source metadata and outputs static WebP; SVG/GIF/other decoders are rejected before image parsing, as are PNG/WebP animation containers. The pipeline limits input bytes, pixel count, processing concurrency (2/process), decoder time (10 seconds), output edge (4096) and output bytes (2,000,000). Authenticated uploads share a durable 12/minute principal limit across website/MCP instances, in addition to the existing request limit.

Objects use immutable random keys in a private bucket. Reads pass through an authenticated same-origin endpoint with no-store, nosniff and sandbox headers; MCP reads return the same verified bytes. No public bucket or permanent signed URLs are used. Object byte length and SHA-256 are checked on every read. Authorization is rechecked after storage retrieval to catch in-flight revocation.

A PostgreSQL transaction locks the owning deck and compares both deck revision and the previous artwork ID for the exact deck/set/card slot before attachment. Named set ownership and visibility are inherited from the owning deck. A rejected concurrent upload cannot overwrite a newer attachment or re-create a deleted deck. Successful replacement best-effort deletes only that slot’s previous object; other sets remain intact. Definitely rejected new objects are cleaned up; uncertain commit outcomes retain their object to avoid deleting potentially committed artwork. Deck deletion cascades metadata. Unreferenced objects from deleted decks, ambiguous commits or failed deletes require an operator-reviewed retention/garbage-collection process; automatic bucket-wide cleanup is deliberately absent. Do not treat database deletion as proof the old object bytes have been physically erased.


## Additive rollout and rollback

Migration 004 adds `arcana_visual_packs` and `arcana_visual_pack_artwork`. It does not alter the original `arcana_card_artwork` table, its primary key, existing JSON or any blob. The original table continues serving `saved-artwork`; the repository adds its pack ID only in API responses. Named images use their own `(deck_id, pack_id, card_slug)` primary key and a composite foreign key to their deck-owned pack. This permits the old deployment to keep reading/writing default images during rollout or rollback. Rolled-back code cannot display named sets, but their rows and blobs remain preserved. Apply the reviewed additive migration before deploying code whose readiness check expects the new tables. No automatic runtime schema creation occurs.

Migration 006 adds only `arcana_visual_pack_assets`, with a deck foreign key and separate `(deck_id, pack_id, slot)` primary key. The default set remains virtual; named-set existence is checked under the owning-deck lock. Existing front rows, legacy JSON, object keys and deck revisions are unchanged. Older code can continue reading/writing fronts after rollback; stored covers/backs remain preserved but undisplayed. Apply the reviewed migration before deploying this version to an artwork-enabled environment: readiness verifies the new table. This PR does not apply it or modify production.

## Explicit activation, isolated preview first

The checked-in feature is disabled by default and creates no bucket, credentials or database schema. Unconfigured website uploads return a clear unavailable response. All values are server-only. Use one dedicated feature-preview environment with a matching database branch, private bucket and narrowly anchored storage credential; do not reuse a production-root credential or configure one root bucket globally across automatic database previews.

1. Review the registered migrations, including `mcp/migrations/006-visual-pack-assets.sql`, then follow the [versioned plan/baseline/apply procedure](domain-migrations.md) against the existing PR105 preview. Use the dedicated migration connection and verified host/database/role. If history is absent, accept only an exact schema-verified baseline; review recovery evidence before baseline/apply. Plan discovers all pending versions, including 006. Verify status and an idempotent second apply before readiness/smoke checks. No runtime schema creation occurs; live application remains blocked until connection, target and baseline are verified.
2. Provision an explicitly approved private bucket on that preview's Neon branch. A separate scoped storage credential is required; current Neon storage credentials are branch+descendant scoped. Creating/configuring that credential requires operator approval and secure secret handling.
3. Configure only that preview branch's server environment:
   - `ARCANA_ARTWORK_ENABLED=true`
   - `ARCANA_ARTWORK_DATABASE_HOST` = the approved database endpoint hostname. Only the exact direct/`-pooler` pair of the same Neon AWS endpoint is treated as equivalent; endpoint ID, cluster, region and domain must all match
   - `ARCANA_ARTWORK_S3_ENDPOINT` = the reviewed HTTPS origin for the **same branch**
   - `ARCANA_ARTWORK_S3_REGION` = its region
   - `ARCANA_ARTWORK_S3_BUCKET` = approved private bucket name
   - `ARCANA_ARTWORK_S3_ACCESS_KEY_ID`
   - `ARCANA_ARTWORK_S3_SECRET_ACCESS_KEY`
4. The explicit database-host pin (with only that narrow direct/pooled equivalence) fails closed if an automatic preview is assigned another DB host. These variables are not assumed to be injected by the Vercel Neon integration. Never place secret values in NEXT_PUBLIC/VITE variables, commit them, print them, or paste them into chat.
5. Verify a neutral one-card upload/read through both website and MCP in that isolated preview, plus unauthorized access and visibility revocation. The first live probe must also confirm Neon accepts conditional `PutObject` (`If-None-Match: *`) and the pinned AWS SDK checksum behavior; the general S3 compatibility docs do not explicitly guarantee those details. The adapter does not silently downgrade those protections. Production activation and whole-deck expansion are separate decisions.

The S3 adapter uses path-style addressing and explicit credentials, so no ambient AWS credential fallback can silently point at a different provider. Endpoint configuration is operator-controlled, not accepted from an upload. Require a private bucket; a public-read bucket would bypass application authorization at the storage origin.
